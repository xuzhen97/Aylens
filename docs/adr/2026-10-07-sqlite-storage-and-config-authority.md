# SQLite 数据所有权与配置来源

- Status: Accepted
- Date: 2026-10-07

## Context

Aylens 的 Gateway 与 Runner 原先从 YAML 加载配置，请求审计仅保存在 Gateway 内存中。日常代理配置需要手工修改文件，且审计在进程重启后丢失。引入管理界面和持久化后，必须明确数据所有权及配置来源，避免 YAML 与数据库互相覆盖，同时保持控制面与执行面的分离。

## Decision

Gateway 与每个 Runner 使用各自独立的本地 SQLite 文件，不共享数据库文件。采用 Node 24 提供的 `node:sqlite`，通过独立存储模块封装版本化迁移、事务、外键校验和关闭生命周期，并验证独立发布包兼容性。

Gateway 保存写入前脱敏的请求审计和配置操作记录，不持久化 Runner 代理凭据。审计仅保存允许的元数据和最多 500 字符的查询摘要；HTTP(S) URL 摘要移除用户信息、全部查询参数与 fragment。默认保留 30 天，分批清理；重启后遗留的运行中请求标记为中断。不保存搜索结果正文、Cookie、请求头或原始异常堆栈。

Runner 保存代理配置、已有 Provider 的主代理和有序备用代理绑定及配置版本。首次初始化时，在同一事务中校验并导入 YAML 中的代理与绑定，记录初始化完成。此后迁移字段以数据库为唯一来源，不再与 YAML 合并或被其覆盖，显式无绑定也不回退到 YAML。内置 `direct` 始终存在且不可删除。

未迁移的 Provider 参数、Browser Profile、插件、路由及启动连接配置继续沿用原有配置方式。Chrome 登录态仍保存在 Runner 本地浏览器用户目录，不迁入 SQLite。数据库与剩余 YAML 配置组装后必须校验引用。

数据库无法打开、迁移失败或损坏时明确报错，不静默回退 YAML 或以内存存储伪装持久化成功，不以空库掩盖已有数据库故障。

## Consequences

- 日常代理修改和审计可跨重启保留，无需引入独立数据库服务或额外原生 SQLite 依赖。
- 每个进程的数据目录及数据库备份需要独立管理；SQLite 不提供本决策中的静态加密，Runner 数据库及备份必须按敏感文件保护。
- YAML 不再能修改已迁移字段；部署文档必须明确首次导入、数据库权威来源和恢复边界。
- 查询摘要并非完全匿名：普通搜索词及 URL 路径仍可能包含隐私。不能将截断和 URL 清理宣称为任意秘密识别。
- 持久化故障需要明确暴露。请求开始审计写入失败时不派发任务；执行期间审计故障不得触发自动重做搜索或声称审计已完整保存。
- 后续扩展配置范围须分别定义所有权、迁移与生效语义，不能把本记录视为完整配置中心的授权。

## Alternatives considered

- **持续从 YAML 合并或启动时覆盖数据库**：会使界面修改失效，且无法明确清除配置，不采用。
- **将整份 YAML 作为数据库中的单个文档**：不能清晰表达引用约束、数据所有权和分项管理，不采用。
- **Gateway 集中保存全部执行配置**：扩大代理凭据集中暴露面并引入离线同步问题，不采用。
- **共享 SQLite 文件或外部数据库服务**：增加跨进程共享与部署复杂度，当前范围不需要。
- **继续内存审计**：无法满足重启后查询历史的需求。
