# 启动装配依赖的可选性边界

- Status: Accepted
- Date: 2026-10-08

## Context

Runner 代理配置管理功能在单元测试中全绿,但在真实启动环境中完全不可用,依次表现为 `Runtime is not connected`、`Secure connection or proxy config support is required` 和页面 404。根因是四处独立的启动装配缺口:`attachRunnerGateway` 漏传配置通道、Runner 入口使用只读 YAML 的旧启动路径而非权威启动装载、配置装载在已初始化分支留下悬空引用、以及服务端静态页面白名单漏注册代理配置页。

这四个缺口的共同形状是:功能实现早已存在且有单元测试覆盖,但真实启动入口从未接上。测试之所以全绿,是因为单测手工构造桩对象绕过了真实的 WebSocket 握手与进程启动;生产代码中漏传依赖不会触发任何编译或测试信号,只会在运行时静默降级为"功能不存在"。

暴露出一个更普遍的问题:`configChannel` 在参数类型上被声明为可选,而系统中并不存在"没有配置通道"这一合法状态。将关键装配依赖声明为可选,等于允许漏传在编译期通过、在运行时无声失败。

## Decision

对依赖注入的可选性采用三层判据,按依赖语义而非调用便利性决定是否必填。

第一类,"系统装配漏了"。依赖是运行时必备组件,不存在缺失的合法状态,漏传属于配置错误。此类依赖必须必填,使漏传成为编译期错误。`attachRunnerGateway` 的 `configChannel` 属此类:`GatewayContext` 中该字段本就非可选,创建上下文时无条件构造,生产调用点唯一,不存在"无需配置通道"的部署形态。

第二类,"配置项缺省"。依赖有完整且安全的有意义缺省值,省略即表示该缺省。此类保持可选。`trustedProxies` 属此类:空数组表示不信任任何代理,是合法且安全的默认值。

第三类,"对端能力事实"。依赖不存在于本系统,由远端真实能力决定,本系统应当如实尊重而非假设。此类保持运行时降级。`capabilities.proxyConfig` 属此类:Runner 未接入权威配置库时上报 false,Gateway 据此拒绝配置请求并返回 `CONFIG_UNSUPPORTED`,这是正确的能力探测行为。

将三类一锅端改为必填是错误的:它会在第二类和第三类的合法场景中迫使人造桩,掩盖真实的部署选项。若将来确需"精简部署不启用代理配置",正确的扩展点是在配置 schema 中引入特性开关,由上下文构造决定是否创建,而不是依赖可选参数要求每个调用方自行记忆传递。

此外约束两处历史上易漏的同步点:服务端静态页面白名单必须与前端路由表同步维护,两者是彼此独立的真相源,后端遗漏仅表现为 404;静态资源根目录在服务启动时一次性解析,前端构建产物缺失时应重新构建并重启服务,而不是反复重试请求。

## Consequences

- 漏传 `configChannel` 现在是 `TS2345` 编译期错误,此类事故在进入运行环境前被拦截。
- 不需要为"无配置通道"场景提供测试造桩,因为该场景不存在;若将来引入,应通过配置开关显式建模。
- 可选性成为需要论证的设计决定而非默认写法,新增注入点时应先判断其属于哪一类。
- 能力降级路径保持端到端可观测:Runner 缺少代理配置能力时,Admin 明确显示该 Runner 不支持编辑,而不是报告 Runner 离线。
- 白名单与前端路由的一致性依赖人工核对,不产生编译信号;改动其中一方时必须同步验证另一方。

## Alternatives considered

- **保留可选依赖但在缺失时启动即报错**:能消除静默降级,但错误推迟到部署后暴露,且无法区分"装配遗漏"与"确实不需要",不采用。
- **将配置通道改为构造参数注入而非选项字段**:可提升必填性,但会改变 `attachRunnerGateway` 的调用形态,当前单一调用点无此收益,不采用。
- **一次性将仓库中所有可选依赖改为必填**:忽略了三层判据,会在配置缺省与能力探测场景引入无谓负担,不采用。
- **仅补充集成测试而不调整类型**:能提高回归覆盖率,但无法在编译期拦截同类遗漏,保留可选声明会诱使后续维护者再次漏传,不采用。
