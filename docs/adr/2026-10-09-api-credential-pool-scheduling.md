# API 凭据池与分层限流

- Status: Accepted
- Date: 2026-10-09

## Context

多 API Key 不能仅靠数组下标轮询。服务商可能对 Key、账号或 Team、接口组施加共享速率或额度限制；网络错误、权限错误和逐 URL 内容失败也不等同于凭据失效。尤其 Exa 的 Team 共享限制说明机械换 Key 会产生无效重试。公共执行机制需兼容服务商差异，而不与浏览器资源管理混淆。

## Decision

Runner 提供独立 API CredentialPool。池绑定一个服务商，Provider 通过池绑定获取凭据，同一服务商的 Search / Extract 可以共享运行状态。不同服务商的 Key 不混用，管理 Service Key 不加入普通检索轮询。

CredentialPool 只负责凭据选择、原子占用与释放、并发容量、冷却及限制协调；服务商适配器负责认证、错误解释和用量语义。选择时先排除禁用、认证失效及额度阻断的凭据，再检查 Key、账号/Team 和接口组容量，在当前可用 Key 中轮询。

错误分类同时表达类别、影响范围及恢复方式。参数错误和逐项内容失败不触发 Key 切换；403 不通用地等同于认证失效。429 优先遵守有效 Retry-After；账号/Team 共享限流时不继续尝试该组兄弟 Key。额度错误依服务商策略解释，范围未知时不能猜测或将整个池永久禁用，也不猜固定重置日期。

所有重试和故障切换受单一总时间及尝试预算约束，不由各层叠加无限重试。网络超时和服务故障不证明 Key 失效，也不保证上游未执行或未计费。全部凭据不可用时明确返回原因，不无限排队。共享服务商故障不得把全部 Key 逐个误标为坏 Key。

人工状态、认证失效、明确额度阻断及必要冷却跨重启保留；瞬时并发占用不持久化，异常和取消必须释放。凭据替换使用版本隔离，旧请求反馈不能污染新秘密的状态。Runner 内安全检测重复 Key，不能将同一秘密重复添加视为额外容量。

CredentialPool 与 Browser Profile / Lease 完全独立。Tavily、Exa、AnySearch 通过 Runner HTTP Transport 直连或代理调用 API，不依赖 Chrome、Cookie 或浏览器租约，支持 API-only Runner。

该池只协调本 Runner 流量。账号分组不是自动验证的归属证明；跨 Runner 使用同一 Key 或账号不能宣称具备全局限流保证。本次不引入中央协调服务，也不在 Key 失效后自动切换匿名访问。

## Consequences

- 新服务商主要增加能力适配及错误/用量策略，而不复制凭据存储、管理 UI 和轮询机制。
- 本机共享限制避免同一账号下的无效换 Key，但管理员须提供正确分组；跨 Runner 协调仍是独立问题。
- 池配置版本与运行健康状态需分离，热更新必须保留未变 Key 的冷却和限制状态。
- 用量保持单位、来源、采集时间和准确性区别，未知值不是零，响应估算费用不是正式账单；查询能力可不存在或需要额外管理凭据。
- API-only Runner 的测试与发布不能要求 BrowserHost；现有浏览器型 Provider 不被迫依赖凭据池。
- 轮询用于授权凭据的负载分摊和可用性，不承诺扩大服务商账号额度或绕过共享限制。

## Alternatives considered

- **每个 Provider 内部维护 Key 数组**：使搜索、提取和多个实例无法清晰共享状态，容易重复实现限流，不采用。
- **只按 Key 限流和停用**：无法表达账号/Team 与接口组共享限制，不采用。
- **统一把所有非成功响应判为坏 Key**：会将参数、权限、内容和服务故障错误隔离为凭据故障，不采用。
- **将凭据与浏览器 Lease 合并为通用资源池**：混淆不同生命周期与安全语义，为 API 调用引入不必要浏览器依赖，不采用。
- **中央跨 Runner Key 调度服务**：引入新的秘密服务和分布式依赖，当前没有已批准的需求，不采用。
