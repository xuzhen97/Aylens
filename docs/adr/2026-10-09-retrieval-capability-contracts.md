# Search / Extract 独立能力契约

- Status: Accepted
- Date: 2026-10-09

## Context

Aylens 已有搜索契约和基于 Provider Plugin 的远程执行。API 检索服务既能搜索，也能提取指定 URL；Tavily、Exa、AnySearch 的参数、原生提取批次和内容格式并不相同。将提取继续塞入搜索字符串，或把某一服务商的接口当作公共契约，会造成调用语义、部分失败和后续扩展的不一致。

## Decision

Search 与 Extract 是独立、按 Provider 声明的执行能力。保留既有 `/v1/search` 及其调用兼容性，新增 `/v1/extract`，以 URL 数组及明确提取来源表达正文获取。旧 Provider 和旧 Runner 不被强制具备新能力；调度须检查目标操作的能力，不支持时明确拒绝。

统一 Extract 返回与输入索引关联的逐 URL 成功或安全失败，以及 completed / partial / failed 总状态。适配器依据服务商的原生批次限制拆分并采用有界并发，所有子调用受共同取消和时间预算约束。不能仅凭 HTTP 200 判定所有项成功，也不因其他项失败重做已成功项。

公共参数只表达准确的共同语义。服务商专属选项使用明确来源命名空间并由适配器严格校验，不支持的显式选项不能静默忽略；调用方不得通过选项注入凭据、认证头或任意 API 地址。搜索可显式利用服务商原生附带正文，不强制另发 Extract 请求，也不默认提取所有搜索结果。

保持 SearchDocument 的 text / snippet 纯文本和 markdown 非可信 Markdown 语义。文档需区分全文、片段、生成摘要与截断，未知格式不能冒充 Markdown。服务商请求 ID 与 Aylens 请求 ID 分离；评分保留来源，不假定不同服务商具有可比尺度。既有 url-fetch 的 URL-as-query 入口继续兼容，不增加隐式跨服务商回退。

## Consequences

- REST、Runner 协议、能力上报、调度及 MCP / VCP 适配必须一致传播新能力和逐项结果，并保留旧搜索行为。
- Search 与 Extract 分离使调用方能控制深读范围、成本和第三方数据披露，但不意味着每次搜索必须发两次网络请求。
- 服务商适配器承担参数、批次和内容差异；公共层不能以统一字段掩盖不支持能力或未知语义。
- 文档内容始终非可信，需限制体积并保留截断信息；目标 URL 仍遵守 Aylens 公网访问策略。
- 本决策不授权 Crawl、Map、Research 或任意自动回退，也不要求所有服务商具备用量查询。

## Alternatives considered

- **以 SearchRequest.query 承载 URL 数组或操作类型**：混淆搜索与提取，难以表达逐项状态，不采用。
- **直接公开 Tavily 请求/响应作为统一接口**：会把 Tavily 特有深度、批次和额度语义固化为其他服务商约束，不采用。
- **为每个服务商建立互不相关的公共 API**：隔离简单，但迫使调用方重复处理共同的提取与失败语义，不采用。
- **默认搜索后提取全部结果**：增加费用、延迟和内容体积，且不尊重调用方需求，不采用。
