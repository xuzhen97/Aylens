# Runner API 凭据所有权与安全管理

- Status: Accepted
- Date: 2026-10-09

## Context

API Provider 需要多个服务商 Key，并通过 Gateway Admin 在线管理。既有 SQLite 数据所有权和 Runner 代理管理决策仅覆盖代理资源，不能被解释为所有执行秘密的集中管理授权。必须明确 API 凭据及池绑定的权威来源、秘密传输和运行生效语义。

## Decision

API 凭据、凭据池及 Provider-to-pool 绑定属于对应 Runner，持久保存在其独立本地 SQLite。数据库是该管理资源唯一权威来源，不从 provider.options 复制秘密，不由启动 YAML 覆盖 Admin 更新。YAML 继续负责插件和 Provider 逻辑部署。绑定必须引用已存在且服务商匹配的池，被引用的池不能直接删除。

Admin 经已认证 Gateway 管理接口及 Runner 配置通道操作在线 Runner。配置消息按资源类型区分，保持既有代理协议兼容并明确声明新增管理能力。沿用管理会话、权限、CSRF、HTTPS / WSS 要求和本机 loopback 开发例外；不建立 Gateway 离线秘密队列。

Gateway 可以短暂接触并转发提交的 Key，但不得持久化、回显或写入日志、审计。Key 只写入，读取返回安全白名单与受限脱敏标识。保留、替换与删除有独立语义，脱敏占位符不得作为真实凭据。上游错误原文同样视为可能含秘密的数据，不透传或整包记录。

写入携带 expectedVersion 和 operationId。Runner 完成校验、本地事务及活动配置原子切换后才确认成功。健康状态变化不修改 Admin 编辑版本。在途已发送请求可完成，停用或删除后不得为新尝试获取该凭据；新任务无需重启 Runner 即使用更新配置。失败不能静默留下持久状态与运行态不一致，无法安全恢复时明确阻断相关新任务。

连接中断或回执超时表示结果待确认，界面重新读取版本和操作标识核对，不自动重复提交秘密。

第一期沿用现有 SQLite 静态保护基线，不新增应用层加密；Runner 数据库及备份必须作为敏感文件保护。后续加密须单独设计外部主密钥、恢复和轮换，不能将密钥与密文同库存放。

## Consequences

- 统一 Admin 可管理远程 Key，但 Gateway 是秘密的短暂处理方，不构成端到端加密或“永远看不到 Key”的保证。
- 数据库权威来源避免 UI 修改被 YAML 覆盖；配置迁移、引用校验和故障恢复必须保持这一所有权。
- 在线确认与版本校验限制并发覆盖，离线 Runner 无法预配置；断线需要用户核对结果。
- 配置通道、启动装配和能力上报均需真实集成验证，不能仅凭手工注入服务的单元测试判定功能可用。
- 数据库与备份泄露可能暴露凭据；部署需实施访问控制，不能宣称第一期已提供静态加密。
- API 执行继续在 Runner；本决策不允许 Gateway 调用目标服务，也不改变 Chrome Cookie 和登录态的边界。

## Alternatives considered

- **Gateway 集中保存并下发 Key**：扩大秘密集中存储面，引入离线同步与额外所有权，不采用。
- **仅 Runner YAML / 环境变量管理**：无法满足已选择的 Admin 在线编辑和持久管理，不采用。
- **YAML 与数据库持续合并**：无法可靠表达清除、启停和权威来源，不采用。
- **保存后重启 Runner**：会影响在途任务，且不能提供预期的在线新请求生效语义，不采用。
- **本次顺带加入静态加密**：主密钥供应、备份恢复与轮换尚无独立批准方案，不纳入第一期。
