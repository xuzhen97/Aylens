# Provider 启用态的运行期权威与 YAML 降级为默认值

- Status: Accepted
- Date: 2026-10-10

## Context

Provider 的 `enabled` 一直是 `config/aylens.yaml` 里的静态字段：判断发生在 `ProviderRegistry.getDefinition()`，实际值来自启动时解析出的配置对象。运维要启停一个 Provider，只能改文件并重启 Gateway。

Admin 界面需要能够点击启停 Provider，这要求该字段在运行期可变且可跨重启保留，同时不能把 YAML 变成程序的可写对象——YAML 由人手工维护，内含环境变量默认值注释与设计说明，程序回写会破坏这些内容，并在只读文件系统或容器部署下直接失败。

`docs/adr/2026-10-07-sqlite-storage-and-config-authority.md` 已确立 Gateway 与 Runner 各自使用本地 SQLite 作为权威存储，并把运行期可变状态（审计、配置操作、Runner 代理配置）迁入数据库；该记录同时声明"后续扩展配置范围须分别定义所有权、迁移与生效语义"。Provider 启用态属于这一类扩展，需要单独记录其所有权与生效语义。

本决策只涉及 Gateway 侧的**路由决策标志**，不需要 Runner 参与：Runner 收到的是派发任务，不判断某个 Provider 是否启用，因此不涉及配置协议或能力位扩展。

## Decision

Provider 的启用/禁用以 Gateway 本地 SQLite 的 `provider_settings` 表为运行期权威，`config/aylens.yaml` 的 `enabled` 降级为**默认值**。

- 该表只存**偏离**：一行代表"操作员的选择与配置文件不同"，无行表示跟随配置文件。生效值为 `覆盖值 ?? 配置值`；"恢复跟随配置"即删除该行，因此不需要额外的状态列，也不存在"清除后仍是覆盖"的中间态。
- 程序**只读不写** YAML。任何代码路径都不得写入 `config/aylens.yaml`。
- 生效判定只发生在 `ProviderRegistry` 一处。对外的只读投影必须读取 registry 的生效值，不得绕过它直接读配置对象。
- 磁盘为权威、进程内映射为缓存，写入顺序固定为"落库成功后再更新内存"；落库失败不得改变内存状态。
- 管理写入路径定位目标 Provider 时使用不做启用检查的查找方式，否则已禁用的 Provider 无法被重新启用。
- 该表为 Gateway 本地状态，与 Runner 数据库无关，也不进入 Runner 配置通道。

## Consequences

- 启停可在 Admin 界面完成，立即生效且跨重启保留，无需触碰 YAML 或重启进程。
- 配置出现两层结构：YAML 表达期望的默认值，数据库表达操作员的覆盖。界面与文档必须显示当前生效值及其来源，否则"文件里写着 false、实际在跑"会成为新的排障陷阱。
- YAML 中已删除的 Provider 会留下**孤儿覆盖行**。这些行不清理：投影只遍历已定义的 Provider，孤儿行天然不可见；若该 id 日后重新出现在 YAML 中，旧覆盖会重新生效。这是有意的取舍——清理不可逆，而保留的成本接近于零。
- 变更只记结构化日志与行的 `updated_at`，**不建立变更事件审计表**。谁能证明"是谁在何时停用了某个 Provider"在当前设计中得不到回答；若治理要求提升，需要新增事件表并回填语义。
- 运行期一致性依赖**单 Gateway 进程**假设。多个实例共用同一数据库时，其他实例的进程内缓存不会实时刷新，需重启后才一致。这与既有配置通道、审计存储的假设相同。
- `enabled=false` 的请求语义**不变**：路由解析仍会选中该 Provider，请求在派发前被拒绝并返回 `PROVIDER_DISABLED`。该错误**不一定**伴随 HTTP 503：检索接口照常返回 200，逐 Provider 的错误在 `meta.providers[].error` 里，且此时不带 `runtimeId`（说明它根本没被派发——这是与上游故障区分的关键特征）；只有错误冒泡到路由层时才映射为 HTTP 503。本决策只让该值从静态变为可翻转，不引入"路由自动跳过禁用 Provider"的行为。
- 启用一个没有可用 Runner 或凭据池的 Provider 不会被拦下，只在调用时失败。
- 本记录扩展了 `2026-10-07-sqlite-storage-and-config-authority.md` 的迁移边界（新增一项由数据库拥有的配置字段），其余未迁移配置的所有权与生效语义仍以该记录为准。

## Alternatives considered

- **界面点击直接回写 `config/aylens.yaml`**：会破坏人工维护的注释与环境变量默认值表达式；需要引入热加载；容器与只读文件系统下直接失效；并发写还引入文件级竞争。不采用。
- **仅保存在进程内存**：实现最简单，但重启即归零，"已经关掉了"会成为假象，比不支持该功能更危险。不采用。
- **在数据库中保存全量启用状态快照**：能省去回落逻辑，但无法表达"恢复跟随配置文件"——一旦写入过，YAML 的默认值就永久失去意义，且两者分歧时无仲裁依据。不采用。
- **在 YAML 与数据库之间持续双向合并**：与既有存储权威记录中已否决的方案同类，会让界面修改被启动时覆盖或使配置无法被明确清除。不采用。
- **把启用状态下发到 Runner，由 Runner 侧判定**：扩大配置协议与能力位面积，而 Runner 本就不做该判断，属于把 Gateway 的路由决策错置到执行面。不采用。
- **禁止停用全部 Provider 或在保存时做可用性预检**：会在控制面引入需要额外维护的例外规则，且"能否真正调用"取决于运行时与凭据状态，保存时无法可靠判定。改为在界面给出影响提示。不采用。
